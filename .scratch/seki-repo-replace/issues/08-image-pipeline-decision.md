# 画像パイプラインの決定

Type: grilling
Status: resolved
Blocked by: 01, 07

## Question

画像の調査結果をもとに、アップロード方式・保存形式・変換を行う場所・配信経路を決める。

## Answer

ADR：[座席レポ画像は投稿時に Go の Lambda で変換し、元画像は残さない](../../../docs/adr/0003-image-pipeline-pregenerate-and-drop-originals.md)

- **アップロード**：presigned POST でブラウザから S3 に直接アップロードする。POST policy は Go の API（ログイン必須）が発行し、サイズの上限・`image/*` だけ許可・保存先のキーを指定する。
- **変換**：S3 イベントで Go の Lambda を起動し、EXIF を取り除いた決まったサイズ（例：一覧用と詳細用。長辺の最大は 1600px）の WebP を作る。Vercel の `<Image />`、AWS 公式の画像変換ソリューション、Lambda@Edge は使わない。
- **元画像**：変換に成功したらすぐに削除する。いちばん大きい変換後の画像を原本として扱う。
- **紐付け**：まず一時置き場（例：`uploads/`）にアップロードし、座席レポの投稿時に画像のキーを送って紐付ける。紐付かなかった画像は、S3 のライフサイクルルールで 1 日後に削除する。
- **配信**：非公開の S3 から CloudFront（OAC）で `img.sekirepo.com` として配信する。料金は従量課金（Always Free）で、定額制の Free プランは使わない。
- **上限（初期値）**：座席レポ 1 件あたり 4 枚、1 枚あたり 15MB。実測して見直す。
- **費用の見込み**：月 300 枚で、Lambda は無料枠の 3% 程度、S3 の保存料金は 1 年後でも月 $0.03 前後。費用の面でのリスクはほぼない。
- 申し送り（バックエンドのマップ）：
  - cgo を使わない WebP エンコーダーの処理時間とメモリを実測する。遅すぎれば JPEG に切り替える。
  - EXIF の Orientation（写真の向き）を自分で補正する。
  - HEIC の扱いを決める（ブラウザ側で JPEG に変換してからアップロードする案も含めて）。
- 申し送り（フロントエンドと UI/UX のマップ）：投稿してから変換済みの画像ができるまでの「処理中」の見せ方を決める。
