# JWT は API Gateway のオーソライザーではなく Go のミドルウェアで検証する

Supabase Auth が発行する JWT は、API Gateway HTTP API の JWT オーソライザーではなく、Lambda の中の Go のミドルウェアで、Supabase の JWKS（公開鍵）を使って検証する。決め手は、ローカルと本番で同じコードが動くこと（ADR 0004）。ローカルの `cmd/api` には API Gateway がないので、オーソライザーに任せると、ローカルでは検証が動かないか、別に検証コードを書くことになる。またユーザー ID の受け取り方も、ローカル（HTTP ヘッダー）と本番（Lambda イベントの `requestContext.authorizer`）で変わってしまう。加えて Go で検証すれば、Supabase が推奨する ES256 と、JWKS のキャッシュを 10 分以内にするという推奨もそのまま守れる。

## Considered Options

- **API Gateway の JWT オーソライザー**：コードが不要で、認証のないリクエストを Lambda の手前で弾ける。ただし、上記のとおりローカルと本番の挙動が分かれる。RSA 系の署名しか扱えないため、Supabase の鍵を RS256（推奨ではないが正式な選択肢）にする必要がある。JWKS を最大 2 時間キャッシュするので、鍵を入れ替えるときは新しい鍵を先に待機状態で公開し、2 時間以上待ってから切り替える必要がある。`nbf` のない JWT の扱いも確認できていない。手前で弾ける利点は、前段の CloudFront の WAF と Lambda の同時実行数の上限があるため小さい。
- **Lambda オーソライザー**：署名方式は自由に選べるが、リクエストのたびに別の Lambda が動き、遅延と管理する関数が増える。
- **共有シークレット（HS256）で検証する**：Lambda に JWT シークレットを持たせることになる。漏れると JWT を偽造できてしまい、Supabase も非推奨としている。

## Consequences

- どのエンドポイントに JWT が必要かは、`openapi.yaml` の `security` で宣言し、ミドルウェアがそれを読む。書き込み系のルートに `security` が付いていなければ失敗するテストで、宣言漏れを防ぐ。
- 「本登録したユーザーだけ」（画像のアップロード）という条件は、業務ルールとして usecase 層で `is_anonymous` を見て判断する。
- Lambda は公開鍵を取得するだけなので、JWT 用の秘密の情報を持たない。
