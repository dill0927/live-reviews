# 座席レポのテーブル

Type: grilling
Status: resolved
Blocked by: 07, 08

## Question

このマップの中心。座席レポのテーブルを設計してマイグレーションにする。
- 4 軸評価の持ち方：今のように列で持つか（`visibility` など 4 列）、軸ごとの行で持つか。評価の範囲（1〜5 か、未評価を許すか）。軸ごとのコメント。
- 座席番号：今のように自由入力の 1 つの文字列か、構造化するか（階・ブロック・列・番など）。会場によって座席の形式が違う点をどう扱うか。
- 参戦日：任意の日付。期間の絞り込みを投稿日から参戦日に変えるか。
- アーティストの参照：必須か任意か。投稿時に新しいアーティストを追加する流れ。
- 匿名投稿：匿名ユーザーの投稿と本登録ユーザーの投稿を同じテーブルで持つ（`auth.users` の id で区別する）前提で、列に違いが出るか。

補足（「Data API の封鎖と DB ロールの権限」から）：`app` にテーブルを作るときは、RLS の有効化・`sekirepo_api` のポリシー・grant の 3 行を必ず書き（ADR 0008）、`make db-test` で確かめる。

補足（「ユーザーのプロフィールと認証との紐付け」から）：投稿者の列は `app.profiles(id)` を参照し、`on delete set null` にする（退会しても座席レポは残り、null は「退会したユーザー」）。投稿する人には、`auth.users` へのトリガーで必ずプロフィールの行がある（匿名ユーザーも）。

## Resolution（2026-10-26）

### 決めたこと
- **テーブルは `app.seat_reports`、投稿者の列は `user_id`**（`app.profiles(id)` を参照、`on delete set null`）。JWT の `sub` と照らし合わせる列なので `profile_id` ではなく `user_id` にした。匿名投稿と本登録の投稿で列の違いは出さない（匿名かどうかは JWT を正とする）。
- **4 軸評価の軸を「見やすさ・ファンサ・周辺施設・アクセス」に変えた**（音響を外し、ファンサを足した）。アイドルファン向けのサービスで、座席について一番知りたいのは「見えるか」と「近くに来るか」のため。用語集の「4軸評価」を書き直し、「ファンサ」を足した。ファンサは「その座席でファンサをもらいやすいか」を、演出（ファンサの多い曲で近くに来るか）も含めて評価する。実際にもらえたかの体験はコメントに書く。
- **4 軸は列で持つ**（`<axis>_rating`・`<axis>_comment` の 8 列）。軸は固定の 4 つなので、行で持つ利点（軸の追加）が効かず、制約と集計を素直に書けるほうを取った。
- **評価は 4 軸とも必須で 1〜5**（`smallint`）。現行は 0〜5 で、フォームの初期値 0 が「未評価」のまま保存され、会場の平均を下げていた。
- **コメントは軸ごとに任意**、1〜1000 文字。ないときは null（空文字は入れない）。
- **座席番号は自由入力の文字列 1 つ**、必須、1〜50 文字。会場や公演によって座席の呼び方が違いすぎるため構造化しない。
- **参戦日 `attended_on` は必須**にした（用語集を「任意」から変更）。2000-01-01 以降、日本時間の今日以前を check で持つ。`current_date` を check に使うのは公式には想定外の使い方だが、「今日以前」は一度通れば通り続けるので、復元で失敗しない。DB は UTC なので `now() at time zone 'Asia/Tokyo'` で比べる。
- **公演名 `show_title` を任意で足した**（1〜100 文字、自由入力）。同じツアーなら会場をまたいで演出の手がかりになる。単発のライブも入るよう、用語を「ツアー名」ではなく「公演名」にした。表記ゆれは許し、必要になったらマスタに昇格する。
- **会場とアーティストは必須で `on delete restrict`**。投稿時に新しいアーティストを追加するときは、Go が同じトランザクションで `artists` に insert してから座席レポを insert する（DB 側に仕組みは要らない）。
- **インデックス**：`venue_id`・`artist_id`・`user_id`。Postgres は外部キーにインデックスを自動で付けない。会場ページの一覧・マイページと、退会時の set null で使う。検索用のインデックスは「読み取りの要件」で決める。
- **権限**：`sekirepo_api` に `select`・`insert`・`delete` と、内容の 12 列だけの `update`。投稿者（`user_id`）と会場（`venue_id`）は替えられない。会場を間違えたら消して投稿し直す。

### 書いたもの
- `supabase/migrations/20261026090000_create_seat_reports.sql`
- `supabase/tests/database/seat_reports.test.sql`（pgTAP・11 件）：必須の列だけで作れる、評価の 0 と null は不可、座席番号の空文字は不可、日本時間の今日は可で明日は不可、座席レポのあるアーティストは消せない、`sekirepo_api` は座席番号を更新できるが投稿者と会場は替えられない、退会すると投稿者が null になる。

### 確かめたこと（ローカル）
- `make db-reset` と `make db-test`（4 ファイル・43 件）が通る。

### 申し送り
- UI/UX のマップへ：会場の平均にファンサを含めるか（ファンサは会場ではなく座席の位置と演出で決まるので、平均の意味は薄い）。公演名の書き方をそろえる誘導（プレースホルダーの例、同じアーティストの既存の公演名を候補に出すなど）。
- 読み取りの要件（霧）へ：期間の絞り込みを投稿日から参戦日に変えるか、公演名での絞り込み。
- 範囲外：現行の座席レポ 4 件といいね 4 件の移行。参戦日がなく必須の列を埋められないため移さない。
