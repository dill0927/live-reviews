# レポ画像といいねのテーブル

Type: grilling
Status: resolved
Blocked by: 09

## Question

座席レポにぶら下がる 2 つのテーブルを設計してマイグレーションにする。
- レポ画像：1 件の座席レポに何枚まで付けられるか。S3 のキーの持ち方。変換中・完了・失敗の状態（画像パイプラインの決定：S3 にアップロード → Lambda が WebP を作る → 元画像は消す）。いつ DB の行を作るか（presigned POST の発行時か、変換の完了時か）。並び順。ログインしたユーザーだけが付けられる、を DB でも保証するか。
- いいね：匿名ユーザーもいいねできるか（JWT は必要だが匿名でもよい、と JWT の検証場所で決まっている）。同じ人の二重いいねを防ぐ一意制約。件数を毎回数えるか、座席レポに件数の列を持つか。

補足（「Data API の封鎖と DB ロールの権限」から）：`app` にテーブルを作るときは、RLS の有効化・`sekirepo_api` のポリシー・grant の 3 行を必ず書き（ADR 0008）、`make db-test` で確かめる。

補足（「座席レポのテーブル」から）：親は `app.seat_reports(id)`。座席レポは物理削除なので、画像といいねの `on delete` を決める。座席レポの投稿者（`user_id`）は退会で null になり得る。

## Resolution（2026-10-26）

### 決めたこと
- **画像は変換が終わってから投稿し、DB の行は投稿時に作る**。投稿フォームが Go に「変換は終わったか」を問い合わせ（Go は S3 にファイルがあるかを見るだけ）、終わるまで投稿ボタンを押せない。「処理中」はフォームの中だけの状態になり、DB の行は変換済みの画像だけを表す。状態の列・null の `seat_report_id`・紐付かなかった行の掃除が要らず、変換 Lambda も DB に接続しない。発行時に行を作る案（状態を DB に持つ）は、Lambda の DB 接続と掃除が増えるので取らなかった。ADR 0003 の Consequences を「投稿の前に変換を待つ」に書き直した。
- **テーブルは `app.report_images`**（`id`・`seat_report_id`・`position`・`created_at`）。座席レポ 1 件に**最大 4 枚**で、`position`（1〜4）と `(seat_report_id, position)` の一意制約で、並び順の重複と 5 枚目を DB で防ぐ。
- **S3 のキーは列に持たず、`id` から規則で組み立てる**。`id` は presigned POST の発行時に Go が決める。サイズ違いを足しても列は増えない。
- **他人の画像の流用は Go が防ぐ**：アップロード先のキーにユーザー ID を入れ（`uploads/<user_id>/<id>`）、投稿時に JWT の本人のものかを確かめる。`id` が主キーなので、同じ画像を 2 つのレポには付けられない。
- **「ログインしたユーザーだけが画像を付けられる」「いいねできる」は Go が JWT の `is_anonymous` で確かめ、DB では保証しない**。匿名かどうかは Auth を正とし DB に写さない（プロフィールと同じ方針）。DB に書けるのは Go だけなので入口で確かめれば足り、変わりうる業務のルールはアプリに置く。
- **編集で画像の付け外しと並べ替えができる**。Go がそのレポの画像の行を消して入れ直す（1 トランザクション）。残す画像は同じ `id` で入れ直すので S3 は動かない。
- **画像の幅と高さ、説明文は持たない**。一覧は決まった比率の枠に収め、代替テキストは座席レポの情報から組み立てる。必要になったら null を許す列を足す。
- **いいねはログインしたユーザーだけ**。匿名ユーザーは IP ごとに 1 時間 30 人まで作れて水増しが簡単なこと、掃除で匿名ユーザーが消えると件数が減ることから。用語集の定義どおりで、匿名の人が押したら本登録に誘う動線にできる。あとから匿名に開くのは Go のチェックを外すだけで済む。
- **テーブルは `app.likes`**（`seat_report_id`・`user_id`・`created_at`）。uuid の `id` は持たず、`(seat_report_id, user_id)` の複合主キーで二重いいねを防ぐ（主キーは件数を数えるインデックスも兼ねる）。`user_id` には別にインデックスを付けた（退会時の cascade とマイページ用）。
- **件数は列に持たず毎回数える**。自分の座席レポへのいいねは禁止しない。
- **`on delete`**：座席レポを消したら画像もいいねも `cascade`、退会したらいいねは `cascade`（画像はレポと一緒に残る）。
- **2 つとも行を作るか消すかだけなので、`updated_at` を持たず、`sekirepo_api` には `select`・`insert`・`delete` だけを与えた**（規約の例外。理由はマイグレーションのコメントに書いた）。

### 書いたもの
- `supabase/migrations/20261026120000_create_report_images_and_likes.sql`
- `supabase/tests/database/report_images_and_likes.test.sql`（pgTAP・10 件）：4 枚は付けられるが 5 枚目と同じ並び順は不可、二重いいねは不可、`sekirepo_api` は更新できないが取り消せる、退会でいいねが消える、座席レポを消すと画像もいいねも消える。
- `CONTEXT.md`：レポ画像（4 枚まで・並び順）、いいね（1 人 1 回・取り消せる・匿名は不可）。
- `docs/adr/0003-image-pipeline-pregenerate-and-drop-originals.md` の Consequences。

### 確かめたこと（ローカル）
- `make db-reset` と `make db-test`（5 ファイル・53 件）が通る。

### 申し送り
- バックエンドのマップへ：S3 のキーの規則（`uploads/<user_id>/<id>` と変換後の場所）、変換が終わったかを返すエンドポイント、投稿時の持ち主の確認、画像の行が消えたら DB のコミット後に Go が S3 のファイルを消す（失敗はログに残し、残ったファイルは許容。気になったら「DB にない画像」を消すジョブを足す）、画像といいねのログイン必須のチェック。
- UI/UX のマップへ：投稿フォームの「処理中」とタイムアウト時の「アップロードに失敗しました」、匿名の人がいいねを押したときの本登録への誘導、会場内の撮影禁止とチケットの写真（QR コード・氏名）を扱う投稿ガイドライン。
- 不適切な画像は、通報と非表示の機能が範囲外なので、当面は運営が SQL と S3 で手作業で消す。
- 確認が必要：匿名ユーザーが無料プランの MAU（50,000）に数えられるか、匿名サインインの制限を超えたときのエラーと解除のタイミング。
